================================================================================
NEXT-BRIDGE  —  DATA FLOW REFERENCE
================================================================================
Last updated: 2026-04-19

This document describes every admin button/function, the API route it calls,
the exact database tables it reads and writes, and the SQL queries you can run
to verify the output at each step.

Admin pages:  /admin → SessionImport section (top) + PlayerRefresh section (below)

================================================================================
DATABASE TABLES
================================================================================

trw_results_raw   Raw scraped data (staging — legacy path only)
  rw_rwid         PK
  rw_source_id    AKBC page ID  (e.g. 660711)
  rw_name1        Player 1 name as scraped from AKBC HTML
  rw_name2        Player 2 name as scraped from AKBC HTML
  rw_percentage   Pair % score as scraped
  rw_imp_score    Pair IMP score as scraped (NULL for MP sessions)

tse_sessions      One row per bridge session
  se_seid         PK (internal session ID)
  se_date         Date  (YYYY-MM-DD)
  se_day_of_week  Monday / Tuesday / Wednesday / Thursday / Friday / Saturday
  se_session_type club / congress / …
  se_scoring      MP (matchpoints) | IMP (international matchpoints)
  se_source_id    AKBC page ID (e.g. 660711)
  se_date_seq     Sequence number within the same date (1, 2, …)

tpl_players       One row per unique player
  pl_plid         PK
  pl_name         Canonical name (title-cased, handles Mc/Mac/O')
  pl_nz_bridge_number  NZ Bridge national number (NULL until filled)
  pl_session_count     Total sessions played (set by Recalculate Averages)
  pl_avg_percentage    Overall average % (set by Recalculate Averages)
  pl_mp_session_count  MP-only session count
  pl_mp_avg_percentage MP-only average %
  pl_imp_session_count IMP-only session count
  pl_imp_avg_percentage IMP-only average %

tre_results       One row per player per session (two rows per pair)
  re_reid         PK
  re_seid         FK → tse_sessions.se_seid
  re_plid         FK → tpl_players.pl_plid  (this player)
  re_partner_plid FK → tpl_players.pl_plid  (their partner)
  re_pairid       FK → tpa_partners.pa_paid (set during import or recalc)
  re_percentage   Converted % score (MP: as scraped; IMP: 0 until Convert IMP→% runs)
  re_imp_score    Raw IMP score (NULL for MP sessions)

tpa_partners      One row per unique player-pair (canonical: plid1 < plid2 by name)
  pa_paid         PK
  pa_plid1        FK → tpl_players.pl_plid
  pa_plid2        FK → tpl_players.pl_plid
  pa_sessions     Total sessions together
  pa_avg_pct      Overall average %
  pa_mp_sessions  MP sessions together
  pa_mp_avg_pct   MP average %
  pa_imp_sessions IMP sessions together
  pa_imp_avg_pct  IMP average %
  pa_last_updated Timestamp of last recalculate

tfl_fetch_log     Log of each Stage 2 "Fetch Results" attempt
  fl_flid         PK
  fl_seid         FK → tse_sessions.se_seid
  fl_fetched_at   Timestamp
  fl_skipped      true = AKBC page returned no data (session not yet posted)
  fl_error        Error message if fetch threw an exception

tam_ambiguous     Players where NZ Bridge lookup returned multiple matches
  am_amid         PK
  am_search_name  The name searched for in tpl_players
  am_nz_number    Candidate NZ# from nzbridge.co.nz
  am_nz_name      Candidate name from nzbridge.co.nz
  am_club         Club listed on nzbridge.co.nz

SESSION IMPORT SECTION  (Admin → top half)
================================================================================

────────────────────────────────────────────────────────────────────────────────
FUNCTION: Manual Session Import  →  "Import Session" button
────────────────────────────────────────────────────────────────────────────────
UI location:   Admin → Manual Session Import
Purpose:       Import a single session by typing its AKBC source ID directly.
               Useful when you know the ID and don't want to load the full list.

API route:  POST /api/scrape/import
Body:       { source_id, day_of_week: "Unknown", session_type: "club",
              scoring: "MP", mode: "skip" | "reimport" }

"Delete & reimport if exists" checkbox:
  - Unchecked (default):  if session already exists → skips silently
  - Checked (reimport):   DELETE tre_results + tse_sessions for that source_id first,
                          then re-imports from scratch

What it does:
  1. Fetches and parses the AKBC results page for that source_id
  2. Detects whether the session is IMP (looks for "teams" or "imp" in page text)
  3. INSERT tse_sessions (se_scoring = 'IMP' or 'MP' based on detection)
  4. For each pair on the page:
     a. Looks up player by NZ# (if present in href) or by name in tpl_players
     b. If not found → INSERT new tpl_players row (name only, NZ# blank)
     c. UPSERT tpa_partners → gets pa_paid
     d. INSERT tre_results for player 1:
          MP session:  re_percentage = scraped pair %,  re_imp_score = NULL
          IMP session: re_percentage = 0.00 (filled later by Convert IMP→%), re_imp_score = raw IMP score
     e. INSERT tre_results for player 2 (same values, roles swapped)

NOTE: ALL session types (MP and IMP) are fully imported in a single pass — session
row, players, results, and partnerships are all written immediately.  For IMP the
raw score is stored now; the percentage equivalent is calculated later by
"Convert IMP→%" (Stage 6, first button).

Tables written: tse_sessions, tpl_players (new players only), tre_results, tpa_partners

Verify:
  SELECT se_seid, se_date, se_day_of_week, se_scoring, se_source_id
  FROM tse_sessions WHERE se_source_id = 660711;

  SELECT re_reid, re_plid, re_partner_plid, re_percentage, re_imp_score
  FROM tre_results
  WHERE re_seid = (SELECT se_seid FROM tse_sessions WHERE se_source_id = 660711);

  -- Count pairs (should be pairs_imported × 2 rows)
  SELECT COUNT(*) FROM tre_results
  WHERE re_seid = (SELECT se_seid FROM tse_sessions WHERE se_source_id = 660711);

────────────────────────────────────────────────────────────────────────────────
FUNCTION: Fetch Session List  →  "Fetch Session List" button
────────────────────────────────────────────────────────────────────────────────
UI location:   Admin → Available Sessions from AKBC  (year dropdown + button)
Purpose:       Loads the full list of sessions available on the AKBC website for
               a given year so you can see what hasn't been imported yet.
               Does NOT write to the database — read-only.

API route:  GET /api/scrape/sessions?year=2026

What it does:
  Scrapes the AKBC calendar page for the selected year and returns a list of
  sessions with their source IDs, dates, and whether each is already in
  tse_sessions.  IMP sessions are flagged separately (greyed out, not selectable
  for batch import via this route — import them via Manual Import instead).

Tables read:  tse_sessions (to mark "already imported")
Tables written: none

────────────────────────────────────────────────────────────────────────────────
FUNCTION: Batch Session Import  →  "Import Selected (N)" button
────────────────────────────────────────────────────────────────────────────────
UI location:   Admin → Available Sessions from AKBC → after selecting rows
Purpose:       Import multiple sessions at once from the AKBC calendar list.
               Same underlying logic as Manual Import, run once per selected row.

API route:  POST /api/scrape/import  (called once per selected source_id)
Body:       { source_id, day_of_week, session_type: "club", scoring: "MP",
              mode: "skip" | "reimport" }

Row statuses shown during import:
  Importing…  = currently being processed
  Done        = imported successfully
  Error       = fetch or insert failed

IMP sessions appear greyed out in the Available Sessions list with an "IMP" badge
and cannot be batch-selected here.  This is because the AKBC calendar page marks
them as team/IMP events before we fetch the results.  To import an IMP session
use Manual Session Import (type the source_id directly).
The import route itself handles IMP fully — the greyed-out behaviour is UI only.

Tables written: same as Manual Import above

────────────────────────────────────────────────────────────────────────────────
FUNCTION: Load Status  →  "Load Status" button
────────────────────────────────────────────────────────────────────────────────
UI location:   Admin → Stage 2 — Fetch Results → "Load Status" button
Purpose:       Refreshes the load status table below it.  Shows all sessions in
               tse_sessions with their pair count, processing state, and any errors.
               Use the Type dropdown (MP / IMP) and Status dropdown (Processed /
               Fetched / Pending / Skipped / No Pairs / Error) to filter the list.

API route:  GET /api/scrape/fetch-results

Status meanings:
  Processed  = pair_count > 0 AND processed flag = true  (results in tre_results)
  Fetched    = pair_count > 0 AND processed = false       (raw data only, not yet in tre_results)
  Pending    = no fetch log entry at all
  Skipped    = last fetch attempt returned no data (AKBC page not posted yet)
  No Pairs   = fetch returned data but parsed 0 pairs
  Error      = last fetch attempt threw an exception

Tables read: tse_sessions, tfl_fetch_log, trw_results_raw (for pair counts)
Tables written: none

Verify:
  SELECT s.se_seid, s.se_date, s.se_scoring,
         COUNT(r.re_reid) AS result_rows,
         MAX(f.fl_fetched_at) AS last_fetch,
         MAX(f.fl_skipped::int) AS was_skipped,
         MAX(f.fl_error) AS last_error
  FROM tse_sessions s
  LEFT JOIN tre_results r  ON r.re_seid = s.se_seid
  LEFT JOIN tfl_fetch_log f ON f.fl_seid = s.se_seid
  GROUP BY s.se_seid
  ORDER BY s.se_date DESC;

────────────────────────────────────────────────────────────────────────────────
FUNCTION: Fetch All Pending  →  "Fetch All Pending" button
────────────────────────────────────────────────────────────────────────────────
UI location:   Admin → Stage 2 — Fetch Results
Purpose:       Re-fetches results from AKBC for every session that has not yet
               been successfully processed (status = Pending, Skipped, or Error).
               IMP sessions are included in this sweep.

               NOTE: For most use-cases Stage 1 import is sufficient. This button
               is mainly useful for sessions imported before the result page was
               posted — they land as Pending and need a follow-up fetch.

API route:  POST /api/scrape/fetch-results  (streaming SSE response)

What it does:
  For each eligible session (pair_count = 0, not previously skipped successfully,
  or IMP sessions regardless of skip history):
  1. Fetches the AKBC results page
  2. DELETE existing trw_results_raw rows for that source_id
  3. INSERT new trw_results_raw rows (rw_name1, rw_name2, rw_percentage, rw_imp_score)
  4. INSERT tfl_fetch_log row (fl_skipped, fl_error)

Tables written: trw_results_raw, tfl_fetch_log

Verify (after fetch):
  SELECT fl_seid, fl_fetched_at, fl_skipped, fl_error
  FROM tfl_fetch_log ORDER BY fl_fetched_at DESC LIMIT 20;

  SELECT rw_source_id, COUNT(*) AS raw_pairs
  FROM trw_results_raw GROUP BY rw_source_id ORDER BY rw_source_id DESC LIMIT 10;

────────────────────────────────────────────────────────────────────────────────
FUNCTION: Refetch Selected  →  "Refetch Selected (N)" button
────────────────────────────────────────────────────────────────────────────────
UI location:   Admin → Stage 2 — Fetch Results → after ticking rows in the table
Purpose:       Same as Fetch All Pending but restricted to the rows you have
               checked.  Use this to retry specific sessions that errored or to
               re-pull a session whose results page has been updated.

API route:  POST /api/scrape/fetch-results?seids=1,2,3  (comma-separated se_seids)

Tables written: trw_results_raw, tfl_fetch_log  (same as above)

Status badges in the table turn to "Importing…" while a session is actively
being fetched.

────────────────────────────────────────────────────────────────────────────────
FUNCTION: Process Results  →  "Process Results" button
────────────────────────────────────────────────────────────────────────────────
UI location:   Admin → Stage 3 — Process Results
Purpose:       Converts raw staging rows (trw_results_raw) into proper player and
               result records.  This is the legacy/alternative path — Stage 1
               import already does this inline.  Use this button only if you have
               raw staging rows that were not processed during import (e.g. from
               an older import pipeline run).

API route:  POST /api/scrape/process-results  (streaming SSE response)

What it does:
  For each unprocessed session in trw_results_raw:
  1. Resolves rw_name1 / rw_name2 to pl_plid values (creates new players if needed)
  2. UPSERT tpa_partners
  3. INSERT tre_results for each player in each pair
  4. Marks the raw row as processed

Tables written: tpl_players (new), tre_results, tpa_partners

Verify:
  SELECT re_reid, re_plid, re_partner_plid, re_percentage, re_imp_score
  FROM tre_results
  WHERE re_seid = <seid>
  ORDER BY re_percentage DESC;

────────────────────────────────────────────────────────────────────────────────
FUNCTION: Fill Missing NZ Numbers  →  "Fill Missing NZ Numbers" button
────────────────────────────────────────────────────────────────────────────────
UI location:   Admin → Stage 4 — Fill Missing NZ Numbers
Purpose:       For every player in tpl_players where pl_nz_bridge_number IS NULL,
               searches nzbridge.co.nz by name and fills in the national number.
               If exactly one match is found → updates immediately.
               If multiple candidates are found → writes to tam_ambiguous for
               manual review (see Assign button below).

               Click the amber "N" count next to "Without NZ#" to show/hide the
               list of player names that still need numbers.

API route:  POST /api/players/refresh?mode=missing  (streaming SSE response)

What it does:
  For each player with no NZ#:
  1. Calls nzbridge.co.nz search API with pl_name
  2. If 1 result:  UPDATE tpl_players SET pl_nz_bridge_number = <found>
  3. If 0 results: records as failed (no update)
  4. If 2+ results: INSERT tam_ambiguous rows for each candidate

Tables written: tpl_players (pl_nz_bridge_number), tam_ambiguous

Verify:
  -- Players still missing NZ#
  SELECT pl_plid, pl_name
  FROM tpl_players WHERE pl_nz_bridge_number IS NULL ORDER BY pl_name;

  -- Ambiguous cases waiting for review
  SELECT am_search_name, am_nz_number, am_nz_name, am_club
  FROM tam_ambiguous ORDER BY am_search_name;

────────────────────────────────────────────────────────────────────────────────
FUNCTION: Assign Ambiguous Player  →  "Assign" button per ambiguous row
────────────────────────────────────────────────────────────────────────────────
UI location:   Admin → Stage 4 → Ambiguous Players table  (Show/Hide toggle)
Purpose:       When Fill Missing found multiple NZ# candidates for a player name,
               each candidate is listed here.  Click Assign on the correct one to
               write that NZ# to the player record and remove the pending row.

API route:  POST /api/players/ambiguous
Body:       { search_name: "John Smith", nz_number: 12345 }

What it does:
  1. UPDATE tpl_players SET pl_nz_bridge_number = nz_number WHERE pl_name = search_name
  2. DELETE FROM tam_ambiguous WHERE am_search_name = search_name

Tables written: tpl_players, tam_ambiguous

Verify:
  SELECT pl_plid, pl_name, pl_nz_bridge_number
  FROM tpl_players WHERE pl_name = 'John Smith';

  SELECT COUNT(*) AS remaining_ambiguous FROM tam_ambiguous;

────────────────────────────────────────────────────────────────────────────────
FUNCTION: Merge Players  →  "Merge (cannot be undone)" button
────────────────────────────────────────────────────────────────────────────────
UI location:   Admin → Stage 4b — Merge Players
Purpose:       Fixes duplicate player records caused by name spelling differences
               in scraped data (e.g. "Kerri Mccrae" vs "Kerrie McCrae").
               Search for the name to KEEP and the name to DISCARD, select both
               from the dropdown, then click Merge.
               ALL historical results transfer to the kept player.
               After merging, run Recalculate Averages + Partnerships to rebuild stats.

               WARNING: This cannot be undone.  Double-check both names before confirming.

API route:  POST /api/players/merge
Body:       { keep_plid: 12, discard_plid: 34 }

What it does (in order):
  1. Fetches keep_name and discard_name from tpl_players
  2. UPDATE trw_results_raw SET rw_name1 = keep_name WHERE rw_name1 = discard_name
  3. UPDATE trw_results_raw SET rw_name2 = keep_name WHERE rw_name2 = discard_name
  4. UPDATE tre_results SET re_plid         = keep_plid WHERE re_plid         = discard_plid
  5. UPDATE tre_results SET re_partner_plid = keep_plid WHERE re_partner_plid = discard_plid
  6. DELETE FROM tpa_partners WHERE pa_plid1 = discard_plid OR pa_plid2 = discard_plid
  7. DELETE FROM tpl_players  WHERE pl_plid  = discard_plid

Tables written: trw_results_raw, tre_results, tpa_partners (delete), tpl_players (delete)

Verify — BEFORE merge:
  SELECT pl_plid, pl_name, pl_session_count
  FROM tpl_players WHERE pl_name ILIKE '%kerri%';

  SELECT re_plid, COUNT(*) AS rows
  FROM tre_results
  WHERE re_plid IN (SELECT pl_plid FROM tpl_players WHERE pl_name ILIKE '%kerri%')
  GROUP BY re_plid;

Verify — AFTER merge + recalculate:
  SELECT pl_plid, pl_name, pl_session_count, pl_avg_percentage
  FROM tpl_players WHERE pl_name ILIKE '%kerrie%mccrae%';
  -- Expect: one row with the combined session count from both duplicates

FUNCTION: Refresh All Stats  →  "Refresh All Stats" button
────────────────────────────────────────────────────────────────────────────────
UI location:   Admin → Stage 5 — Refresh All Stats
Purpose:       For every player that has an NZ# assigned, fetches their current
               grade, rating, and masterpoints total from nzbridge.co.nz and

What it does:
  For each tpl_players row where pl_nz_bridge_number IS NOT NULL:
  1. Calls nzbridge.co.nz player profile endpoint

Tables written: tpl_players (grade / rating / masterpoints columns)

  SELECT pl_plid, pl_name, pl_nz_bridge_number, pl_grade, pl_rating, pl_masterpoints
  FROM tpl_players
  WHERE pl_nz_bridge_number IS NOT NULL
  ORDER BY pl_masterpoints DESC NULLS LAST
  LIMIT 20;

────────────────────────────────────────────────────────────────────────────────
FUNCTION: Convert IMP → %  →  "Convert IMP → %" button
────────────────────────────────────────────────────────────────────────────────
UI location:   Admin → Stage 6 — Recalculate  (FIRST button — run before averages)
Purpose:       Translates raw IMP scores into comparable percentage equivalents
               so that IMP and MP sessions can be averaged together.
               Formula: worst pair in session → 25%, best pair → 75%, equal → 50%.
               Must be run BEFORE Recalculate Averages whenever a new IMP session
               is imported.

API route:  POST /api/players/recalculate?mode=imp-convert  (streaming SSE)

What it does:
  Finds every session that has at least one re_imp_score IS NOT NULL, then for
  each such session:
  1. SELECT MIN(re_imp_score), MAX(re_imp_score) for the session
  2. UPDATE tre_results
     SET re_percentage = ROUND(
       CASE WHEN max = min THEN 50
            ELSE 25 + ((re_imp_score - min) / (max - min)) * 50
       END, 2)
     WHERE re_seid = <seid> AND re_imp_score IS NOT NULL

Tables written: tre_results (re_percentage column only)

Verify:
  -- Confirm percentages are in 25-75% range for an IMP session
  SELECT re_plid, re_imp_score, re_percentage
  FROM tre_results
  WHERE re_seid = (SELECT se_seid FROM tse_sessions WHERE se_source_id = 660711)
  ORDER BY re_imp_score DESC;
  -- Highest IMP → re_percentage ≈ 75.00
  -- Lowest  IMP → re_percentage ≈ 25.00

  -- Before running: IMP rows show re_percentage = 0.00
  -- After running:  all IMP rows have re_percentage between 25 and 75

────────────────────────────────────────────────────────────────────────────────
FUNCTION: Recalculate Averages  →  "Recalculate Averages" button
────────────────────────────────────────────────────────────────────────────────
UI location:   Admin → Stage 6 — Recalculate  (second button)
Purpose:       Recomputes each player's session count and average percentage from
               tre_results.  Run this after any import, reimport, merge, or
               after Convert IMP→% has updated percentages.

API route:  POST /api/players/recalculate?mode=averages  (streaming SSE)

What it does:
  For each distinct re_plid in tre_results (joined to tse_sessions for scoring type):
  1. Computes: total count, overall avg, MP-only count + avg, IMP-only count + avg
  2. UPDATE tpl_players SET
       pl_session_count      = total count,
       pl_avg_percentage     = overall avg,
       pl_mp_session_count   = MP count,
       pl_mp_avg_percentage  = MP avg,
       pl_imp_session_count  = IMP count,
       pl_imp_avg_percentage = IMP avg
     WHERE pl_plid = <plid>

Tables written: tpl_players (all count and average columns)

Verify:
  SELECT pl_plid, pl_name,
         pl_session_count, ROUND(pl_avg_percentage,2) AS avg,
         pl_mp_session_count, ROUND(pl_mp_avg_percentage,2) AS mp_avg,
         pl_imp_session_count, ROUND(pl_imp_avg_percentage,2) AS imp_avg
  FROM tpl_players
  WHERE pl_name ILIKE '%McCrae%';

  -- Cross-check manually:
  SELECT COUNT(*) AS rows, ROUND(AVG(re_percentage),2) AS avg
  FROM tre_results WHERE re_plid = <plid>;

────────────────────────────────────────────────────────────────────────────────
FUNCTION: Recalculate Partnerships  →  "Recalculate Partnerships" button
────────────────────────────────────────────────────────────────────────────────
UI location:   Admin → Stage 6 — Recalculate  (third button)
Purpose:       Rebuilds tpa_partners aggregate stats from tre_results.  Also
               back-fills re_pairid on any tre_results rows that are missing it.
               Run after Recalculate Averages.

API route:  POST /api/players/recalculate?mode=partners  (streaming SSE)

What it does:
  1. Queries tre_results grouped by (re_plid, re_partner_plid) where plid < partner_plid
     to get: sessions, avg %, MP sessions, MP avg, IMP sessions, IMP avg
  2. Orders the pair so plid1/plid2 follow alphabetical name order
  3. UPSERT tpa_partners (conflict on pa_plid1, pa_plid2)
  4. UPDATE tre_results SET re_pairid = pa_paid
     WHERE re_pairid IS NULL  (back-fills any rows inserted without a pair ID)

Tables written: tpa_partners (all columns), tre_results (re_pairid)

Verify:
  -- Partnership stats for a player
  SELECT pa_paid, p1.pl_name, p2.pl_name,
         pa_sessions, ROUND(pa_avg_pct,2) AS avg,
         pa_mp_sessions, pa_imp_sessions
  FROM tpa_partners pa
  JOIN tpl_players p1 ON p1.pl_plid = pa.pa_plid1
  JOIN tpl_players p2 ON p2.pl_plid = pa.pa_plid2
  WHERE pa.pa_plid1 = <plid> OR pa.pa_plid2 = <plid>
  ORDER BY pa_sessions DESC;

  -- Check no results rows are missing their pair ID
  SELECT COUNT(*) AS missing_pairid FROM tre_results WHERE re_pairid IS NULL;

────────────────────────────────────────────────────────────────────────────────
FUNCTION: Recalculate Date Seq  →  "Recalculate Date Seq" button
────────────────────────────────────────────────────────────────────────────────
UI location:   Admin → Stage 6 — Recalculate  (fourth button)
Purpose:       Assigns se_date_seq = 1, 2, … to sessions that share the same
               calendar date (ordered by se_seid).  Used by the UI to distinguish
               multiple sessions on the same day (e.g. Monday morning vs evening).
               Run once after a bulk import or any time sessions are added.

API route:  POST /api/players/recalculate?mode=dateseq  (streaming SSE)

What it does:
  UPDATE tse_sessions s
  SET se_date_seq = ranked_seq
  using ROW_NUMBER() OVER (PARTITION BY se_date ORDER BY se_seid ASC)

Tables written: tse_sessions (se_date_seq column)

Verify:
  SELECT se_date, se_date_seq, se_seid, se_day_of_week, se_scoring
  FROM tse_sessions
  ORDER BY se_date DESC, se_date_seq ASC
  LIMIT 20;


================================================================================
TYPICAL FULL WORKFLOW — NEW SESSION
================================================================================

Step 1  — Import the session  (ALL session types — MP and IMP)
  Admin → Manual Session Import (type source_id)
       or Available Sessions → Import Selected  (MP sessions; IMP greyed out — use Manual)
  → tse_sessions row inserted (se_scoring = 'MP' or 'IMP' auto-detected)
  → tpl_players rows created for any new players
  → tre_results rows inserted (2 per pair):
         MP session:  re_percentage = scraped pair %,  re_imp_score = NULL
         IMP session: re_percentage = 0.00 (pending),  re_imp_score = raw IMP score
  → tpa_partners rows upserted

Step 2  — IMP ONLY: Convert IMP → %
  Admin → Stage 6 → Convert IMP → %   (run BEFORE averages)
  → tre_results.re_percentage updated to 25–75% range for IMP rows

Step 3  — Recalculate Averages
  Admin → Stage 6 → Recalculate Averages
  → tpl_players averages and session counts updated

Step 4  — Recalculate Partnerships
  Admin → Stage 6 → Recalculate Partnerships
  → tpa_partners stats rebuilt
  → tre_results.re_pairid back-filled where NULL

Step 5  — Recalculate Date Seq  (once after bulk import)
  Admin → Stage 6 → Recalculate Date Seq
